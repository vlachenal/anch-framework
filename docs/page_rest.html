AnCH REST library documentation

Introduction

AnCH REST library declares REST APIs independently of HTTP servers, and provides an HTTP client over native HTTP libraries (see anch-rest.todo for the work in progress).

Libraries

  • anch-rest-common : HTTP model (Method, Status, Headers, MediaType, Request, Response) and codecs (Json based on anch-json, Text).
  • anch-rest-server : endpoints declaration and routing (Api).
  • anch-rest-client : HTTP client (Client) over a Transport.
  • anch-rest-curl : libcurl transport (CurlTransport), option ANCH_REST_CURL .
  • anch-rest-nginx : nginx applications bridge (ANCH_REST_APPLICATION ), option ANCH_REST_NGINX , and nginx module sources (nginx/ , installed in share/anch/nginx-module ).
  • anch-rest-protobuf : Protocol Buffers codecs (Protobuf, ProtobufJson) and RPC services (RpcService) served in an API with Connect and gRPC-Web protocols, Connect client ; option ANCH_REST_PROTOBUF (built when Protobuf is found).
  • anch-rest-grpc : gRPC server (GrpcServer) for the same RPC services ; option ANCH_REST_GRPC (built when gRPC is found).
  • anch-rest-thrift : Apache Thrift codecs (ThriftBinary, ThriftCompact, ThriftJson), Thrift services in an API (installThrift) and Thrift transport over the client (ThriftTransport) ; option ANCH_REST_THRIFT (built when Thrift and Boost headers are found).

Endpoints declaration

Endpoints are declared with a method and a path pattern. Endpoint function arguments are bound from the request: [const Request&], path parameters..., [Body<T>]. The result is serialized with the codec negotiated with Accept header:

anch::rest::Api api;
api.get("/pets/{id}", [](uint64_t id) -> std::optional<Pet> { return findPet(id); }) // 404 when empty
.produces<anch::rest::Json>();
api.post("/pets", [](anch::rest::Body<Pet> pet) {
Pet saved = savePet(*pet);
return anch::rest::Response(anch::rest::Status::CREATED)
.header(anch::rest::header::LOCATION, "/pets/" + std::to_string(saved.id));
})
.consumes<anch::rest::Json>();
api.filter([](anch::rest::Request& request, const anch::rest::Next& next) {
if(!request.getHeaders().has(anch::rest::header::AUTHORIZATION)) {
return anch::rest::Response(anch::rest::Status::UNAUTHORIZED);
}
return next(request);
});
api.validate(); // every endpoint has its codecs
anch::rest::Request request(anch::rest::Method::GET, "/pets/1");
anch::rest::Response response = api.handle(request); // done by HTTP server adapter

Forms

Form is an ordered list of Part (fields and files, a name can be repeated). FormUrlEncoded codec reads and writes application/x-www-form-urlencoded bodies and Multipart codec reads and writes multipart/form-data bodies (with files); fields are converted on server side like query parameters:

api.post("/login", [](anch::rest::Body<anch::rest::Form> form) {
std::string user = anch::rest::requiredFormField<std::string>(*form, "user"); // 400 when missing
std::optional<bool> remember = anch::rest::formField<bool>(*form, "remember"); // 400 when invalid
...
})
.consumes<anch::rest::FormUrlEncoded>();
client.post("/login").body<anch::rest::FormUrlEncoded>(anch::rest::Form().add("user", "rex").add("password", pwd)).send();
api.post("/pets/{id}/photo", [](uint64_t id, anch::rest::Body<anch::rest::Form> form) {
const anch::rest::Part* photo = form->part("photo"); // file name, media type, content
...
})
.consumes<anch::rest::Multipart>();
anch::rest::Form upload;
upload.add("description", "Rex").addFile("photo", "rex.png", anch::rest::MediaType("image", "png"), content);
client.post("/pets/{id}/photo", 42).body<anch::rest::Multipart>(upload).send();

Bodies are limited by side (FormLimits : body size, number of parts, part size, part headers size): over a limit, server answers 413 .

Large files do not need memory: multipart parts larger than FormLimits::maxMemoryPartSize (1 MiB) are read in temporary files (deleted with their last part copy), parts are written from their file and the client streams multipart bodies ( Content-Length is known, libcurl transport reads the stream):

anch::rest::FormLimits& limits = anch::rest::Multipart::limits(anch::rest::Side::SERVER);
limits.maxSize = limits.maxPartSize = 1024 * 1024 * 1024; // 1 GiB uploads, read in temporary files
limits.temporaryDirectory = "/var/tmp/uploads";
anch::rest::Form upload;
upload.add(anch::rest::Part::fromFile("video", "/data/video.mp4", anch::rest::MediaType("video", "mp4")));
client.post("/videos").body<anch::rest::Multipart>(upload).send(); // read from the file while it is sent

CORS

Cross-Origin Resource Sharing is enabled on the API. Allowed methods are the methods of the routes matching the path. Preflight requests are answered before filters (they have no credentials) and CORS headers are added to every response, errors included:

api.cors({
.origins = {"https://app.example.com"}, // "*" for every origin
.headers = {"Content-Type", "Authorization"}, // "*" for every requested header
.exposedHeaders = {"Location"},
.credentials = true, // not allowed with "*" origin
.maxAge = std::chrono::hours(1)
});
anch::rest::Api::cors
Api & cors(anch::rest::CorsOptions options)

A preflight with a not allowed origin, method or header is answered with 403 without CORS headers. Vary: Origin is added when origins are listed.

Client

Path placeholders are replaced in order and percent-encoded. Accepted codecs are part of the call type: as<T>() is checked at compile time and deserializes the response with the codec matching its Content-Type :

anch::rest::TransportConfig config;
config.timeout = std::chrono::seconds(5);
anch::rest::Client client(std::make_unique<anch::rest::CurlTransport>(config), "https://api.example.com/v1");
client.filter(anch::rest::bearerAuth(token));
Pet pet = client.get("/pets/{id}", 42).accept<anch::rest::Json>().as<Pet>(); // HttpError when status >= 400
anch::rest::Response created = client.post("/pets").body<anch::rest::Json>(pet).send();
client.del("/pets/{id}", 42).execute();

Fields constraints

anch-json fields constraints ( anch::json::required , anch::json::minLength , ...) are checked by the Json codec according to the side which uses it ( Side ):

  • server: request bodies are checked (invalid body: 400 response, its body is the error message with the path of the invalid value, such as /name: Length 0 is lower than minLength 1), responses are not ;
  • client: request bodies are checked before being sent ( body<Json>(value) raises anch::json::MappingError , nothing is sent), server responses are trusted and read with tolerance (unknown fields are ignored, indented responses are accepted).

Each side has its own mapping options (server and client can run in the same process), which can be changed at application initialization:

anch::rest::Json::options(anch::rest::Side::SERVER).serialize_check_constraints = true; // also check responses
anch::rest::Json::options(anch::rest::Side::CLIENT).deserialize_ignore_unknown_field = false; // strict client

Apache Thrift

Structures generated by thrift –gen cpp are read and written by ThriftBinary ( application/vnd.apache.thrift.binary ), ThriftCompact ( .compact ) and ThriftJson ( .json ) codecs. Thrift services are served over HTTP by an API, as Thrift THttpServer (the protocol is chosen with the Content-Type , application/x-thrift is the binary protocol), and generated clients call them through an anch-rest client:

An application is a shared library which declares its API factory:

Libraries are loaded when configuration is read (nginx -t reports loading errors) and APIs are created in each worker process.

Request and response bodies are streamed (anch::cutils::CIStream and anch::cutils::COStream on the module C functions):

  • in a thread pool, the handler is started as soon as request headers have been read. It reads the request body while nginx receives it (unbuffered body: at most client_body_buffer_size bytes are waiting for the handler), and its response body is sent while it is written, with at most anch_rest_buffers in memory: the handler waits while they are being sent ;
  • the response is started (status and headers) when more than one buffer has been written, with chunked transfer encoding, or at the end of the body with its Content-Length when it fits in one buffer. An error raised before the start is answered with 500 , an error raised after closes the connection (truncated response) ;
  • an application can stream a large response with Response::stream ; the request outlives the response body writer, which can read the request body ;
  • a slow client keeps a thread pool thread busy while it sends its request body, or receives the end of a response larger than buffers: thread pool size, client_body_timeout and send_timeout bound it ;
  • without thread pool (anch_rest_thread_pool off ), the handler is executed in the event loop: the request body is buffered by nginx (memory, then temporary file) and read in blocks, and the response body is given to nginx as it is written, without flow control (a large response stays in memory until it has been sent).
