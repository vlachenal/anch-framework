AnCH OAS library documentation

Introduction

AnCH OAS library parses OpenAPI 3.0 documents and generates C++ code from them: anch-oas-gen generates C++ structures and enumerations from the document schemas ( components.schemas ) with their anch-json mappers, so that API payloads can be deserialized (and serialized) with anch::json::deserialize and anch::json::serialize . With --server and --client options, it also generates anch-rest endpoints from the document paths: a service interface registered in anch::rest::Api and a typed client (see Endpoints ).

Prerequisites

AnCH OAS depends on anch-json (document parsing) and anch-cli ( anch-oas-gen arguments). Generated code depends on anch-json, on anch-uuid when uuid format is used, and on anch-date when date-time or date formats are used (linked by anch-json when ANCH_DATE is ON ).
Documents have to be in JSON format (YAML is not supported). Swagger 2.0 and OpenAPI 3.1 documents are refused.

Installation

anch-oas is built with ANCH_BUILD_OAS option (ON by default) ; cmake --install installs anch-oas-gen with the libraries.

Usage

anch-oas-gen -i petstore.json -o gen -n petstore::model -f petstore # generates gen/petstore.hpp and gen/petstore.cpp
cat petstore.json | anch-oas-gen -o gen # document on standard input: gen/models.hpp and gen/models.cpp

Options:

  • -i / --input : OpenAPI document (default to standard input) ;
  • -o / --output : output directory, created when needed (default to current directory) ;
  • -n / --namespace : models namespace (default to model ) ;
  • -f / --file : generated files base name (default to models ) ;
  • --no-uuid : uuid format is mapped to std::string instead of anch::UUID ;
  • --no-date : date-time and date formats are mapped to std::string instead of anch::date::Date and std::chrono::year_month_day ;
  • --server : generates the service interface and its endpoints registration ( NAME-server.hpp and NAME-server.cpp ) ;
  • --client : generates the typed client ( NAME-client.hpp and NAME-client.cpp ) ;
  • --api-name : service and client names prefix (default to the document title in PascalCase) ;
  • --no-constraints : value constraints are not generated ;
  • --strict : unsupported schemas and operations raise an error instead of a warning.

Unchanged files are not rewritten. With CMake, a stamp file tracks the generation:

set(models_dir ${CMAKE_CURRENT_BINARY_DIR}/gen)
add_custom_command(
OUTPUT ${models_dir}/petstore.stamp
BYPRODUCTS ${models_dir}/petstore.hpp ${models_dir}/petstore.cpp
COMMAND anch-oas-gen -i ${CMAKE_CURRENT_SOURCE_DIR}/petstore.json -o ${models_dir} -n petstore::model -f petstore
COMMAND ${CMAKE_COMMAND} -E touch ${models_dir}/petstore.stamp
DEPENDS ${CMAKE_CURRENT_SOURCE_DIR}/petstore.json)
add_custom_target(petstore-models DEPENDS ${models_dir}/petstore.stamp)
add_executable(petstore main.cpp ${models_dir}/petstore.cpp)
add_dependencies(petstore petstore-models)
target_include_directories(petstore PRIVATE ${models_dir})
target_link_libraries(petstore PRIVATE anch::json anch::uuid)

  • Optional and nullable properties are std::optional ; arrays and maps are empty when absent.
  • Required properties are registered with anch::json::required : deserialization fails when they are absent ( MISSING_FIELD ) or null while they are not nullable ( CONSTRAINT_VIOLATION ).
  • Inline objects and enumerations are named after their path: <Model><Property> , <Model><Property>Item for array items and <Model><Property>Value for map values.
  • allOf merges the properties of every schema: inherited properties keep the types of the model which declares them.
  • Recursive references (a model which contains itself directly or through other models) are std::shared_ptr ; recursion through arrays and maps does not need pointers.
  • Member names are property names where invalid characters are replaced by _ ; C++ keywords and macros get a _ suffix ( class → class_ ). Enumeration values are upper case words ( in-stock and inStock → IN_STOCK ).
  • Properties are declared in alphabetical order (anch-json maps are ordered).
  • Models have a default operator== (every member is compared).

Constraints

Schema constraints are generated as anch-json constraints given to registerField , and checked on deserialization, and on serialization when serialize_check_constraints option is enabled ( CONSTRAINT_VIOLATION error with the path of the value, see anch-json for client and server recommended options). They are listed in the generated documentation of each member. --no-constraints disables them (required properties are still checked). Generated models can be checked without serialization with anch::json::validate (every violation is returned, see anch-json).

non string enum (numbers, booleans) anch::json::allowed<T>({...})

array items and map additionalProperties constraints anch::json::items(...)
  • Numbers are written as in the document (no conversion: integers bounds can be greater than 2^53). A bound outside the range of the C++ integer type is reported with a warning.
  • Constraints of alias components are applied where they are used: "$ref": "#/components/schemas/Code" with Code a string with minLength gets the minLength constraint.
  • Constraints which can not be applied are ignored with a warning (error with --strict ): minLength on an integer, multipleOf which is not strictly positive, enum value which is not a value of the type, invalid pattern , ... String constraints of uuid , date-time and date formats are ignored without warning: values are checked by their parser.

Limitations

The following schemas are not generated (warning, or error with --strict ):

  • oneOf / anyOf compositions (anch-json does not support polymorphism) ;
  • free-form objects and schemas without type (anch-json has no generic JSON value type) ;
  • nested containers: array of arrays, map of arrays, ... ;
  • references outside #/components/schemas/ .

Properties which have not been generated are unknown fields for anch-json: use deserialize_ignore_unknown_field to accept them. Formats without registered validator ( password , ...) are not checked: validators can be added with anch::json::registerFormat . Constraints of component schemas which are deserialized directly (alias of array deserialized as root value) are not checked: only properties constraints are.

Endpoints

With --server and --client , each operation of the document paths ( get , put , post , delete and patch ) is a method of the <API>Service interface (server side) and of the <API>Client class (client side). Both are in the models namespace and depend on anch-rest ( anch::rest-server and anch::rest-client CMake targets).

// Server: implement the service and register its endpoints
class Store: public petstore::model::PetStoreService {
public:
std::optional<petstore::model::Pet> getPet(int64_t id) override; // GET /pets/{id} (404 when empty)
petstore::model::Tag createTag(const petstore::model::Tag& body) override; // POST /pets (201)
// ...
};
Store store;
anch::rest::Api api;
petstore::model::registerEndpoints(api, store);
api.validate();
// Client: typed calls over an anch-rest client (transport, base URL and filters are configured by the caller)
anch::rest::Client rest(std::make_unique<anch::rest::CurlTransport>(), "https://api.example.com");
petstore::model::PetStoreClient client(rest);
std::optional<petstore::model::Pet> pet = client.getPet(1);
std::vector<petstore::model::Tag> tags = client.listPets("AB"); // optional query parameters default to std::nullopt

Generation rules:

  • method name: operationId in camelCase ( get-pet → getPet ), derived from the method and the path when it is missing ( DELETE /pets/{id} → deletePetsById , with a warning) ;
  • arguments: path parameters in path order, request body ( const T& body ), required query parameters, optional query parameters ( std::optional ). Path item and operation parameters are merged, references to #/components/parameters/ are followed. Path and query parameters are strings, numbers, booleans or UUID (converted by anch::rest::ParamConverter : invalid or missing value is a 400 response) ;
  • request body: application/json ( anch::rest::Json ) and text/plain ( anch::rest::Text , strings only) ; references to #/components/requestBodies/ are followed ;
  • result: success response ( 2xx ) with content → its type, with a 404 response → std::optional (empty result is a 404 response server side, 404 response is an empty result client side), without content → void , several success responses or other media types → anch::rest::Response . Status other than 200 (or 204 for void ) is set with Endpoint::status ( 201 , 202 , ...). Error responses are not generated: client raises anch::rest::HttpError ;
  • inline schemas of bodies and responses are models named <Operation>Request and <Operation>Response , with their constraints (checked as described in anch-rest).

Not generated (warning, or error with --strict ): head , options and trace operations (anch-rest serves HEAD with GET routes), path segments which are not whole parameters ( /files/{name}.json ), undeclared path parameters, parameters of other types (enumerations, arrays, objects), request bodies of other media types. Header and cookie parameters are not generated (warning). Constraints of path and query parameters are not checked.
